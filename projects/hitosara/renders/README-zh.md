# `renders/` — 编辑做出来的东西（作品）的放置处

> **影像不是生成的。是被编辑的。**

**`media/` 是标本的放置处，这里是作品的放置处。**

| | |
|---|---|
| `media/` | **标本。** 生成器返回的东西。每个镜头有几本 |
| `renders/` | **作品。** 把标本选出来、切断、接起来的东西 |

⚠️ **即使是同一条视频，放置的地方不同，意义就不同。** 把标本放进 `renders/`，它就长着作品的脸，
**把作品放进 `media/`，它就长着「没有记录的镜次」的脸。**

⚠️ **用手接起来的东西也在这里。** 是用手做的还是基盘做的，**不改变放置的地方**
——**作品就是作品。**

## ⚠️ 为什么不按名字区分

`media/README.md` 定下「文件名以 `NN__` 开头」。**那个方案被丢掉了。**
⚠️ **那个拼写被作者的手改写过许多次**——在我看着的时候也在动。
**会动的规则，运不了区分。** 所以**用地方来分。**

⚠️ **不要放进 `takes/`。** 那边是**记录**（`*.yaml`）。
放进去，**`L25` 就会读它，`provider.model` 就成了谎话**——**这不是镜次。**

## ⚠️ 不要只放物

`renders/` 的每一本，都**需要一张声称它的记录**——否则
**和 `02_20260913-….mp4` 一样的洞会再次打开**（实体与记录矛盾，而机器不会报警）。

⚠️ **这条规则现在被破着。** 下面「现在存在的东西」里的那2本，
**在 `timeline/` 里都没有记录**——因为声称它的记录写不出来（下一节）。
**写了规则，和规则被守着，是两回事。**

**规则: `renders/<名称>.mp4` 的名称，与生出它的 `timeline/<名称>.yaml` 相同。**
⚠️ **方向只有一个**——**记录声称物。物不声称记录**（副本会相互矛盾）。

⚠️ **但是，`timeline.schema.json` 里没有声称渲染文件的栏位。**
放进 `interchange`（`additionalProperties: true`）就能写，但**那不是「有栏位」。**
**所以，现在写不出读这条规则的检查。是个洞。**

## ⚠️ 现在，记录的一侧写不出来

**即使接起来的东西存在，声称它的 `timeline/` 记录现在也写不出来。**
`clips[]` 要求 `shot` 与 `take`（`schemas/timeline.schema.json`）——但
**视频的镜次里，`adopted: true` 一本都没有**（`02` 与 `06` 是 `false`。其余什么都没有写）。
**也就是说，哪个标本以什么顺序排的，不在记录的一侧。**

⚠️ **选别是作者的工作。** 说「这 N 本，按这个顺序」，那就是记录。
**在那之前，这个目录里的物，从记录里拉不出来。**

## ⚠️ 这个目录的空与充实，都不会被报告

与 `timeline/` 相同。`takes/` 的空会被报告（「一本都没有」）。
**这边谁都不读**——**不报告的检查，看起来和通过的检查一样。**

⚠️ **`.mp4` 已经由 `.gitattributes` 用 LFS 追踪**（与 `media/` 相同）。
⚠️ **只是放下，并不会成为 LFS。** 只有 `git add` 之后才会变成133字节的指针。
⚠️ **`git lfs ls-files` 的第2列，不是手头实体的有无。**
`*` 指「完整的对象」，`-` 指「**LFS 指针**」（`git lfs ls-files --help`）——
也就是说，它是**磁盘上的副本是指针（或不存在）**这一点的标记，
**并不说明 `.git/lfs/objects/` 里有没有实体。**（与 `media/README.md` 相同）

## 现在存在的东西

⚠️ **不要写数量**——数量会动，**写下来就会矛盾。** 要数就去读 `git lfs ls-files`。
存在的是**2本**——**同一个画面，只有声音的有无不同。**

| | |
|---|---|
| `hitosara.mp4` | **无声。** 作者用手接起来的版。**这部作品画面的正典** |
| `hitosara+soft-gold-sky.mp4` | **同一个画面＋ `soft-gold-sky`。** 要公开的版 |

⚠️ **`+` 是「画面相同、声音加上去了」的标记。** 画面没有重新编码（`-c:v copy`）。

⚠️ **这个版已经公开了**——在作者自己的频道上
（YouTube，`https://www.youtube.com/watch?v=pJyiziIUaPY`）。
**下面的音乐记录载在那个视频的说明栏里**——所以
「连这张表一起带走」这个条件，在那里是满足的。

⚠️ **但是，YouTube 上的东西，和这个目录里的东西，不是同一个物。**
YouTube **配的是它自己的编码**，而且⚠️ **上传的文件是这一个，
还是为它做的更轻的版，哪里都没有写。**
**存在两个面，哪个是正典没有决定**——**而且没有检查会为这个报警**
（如上所述，`renders/` 谁都不读）。

### ⚠️ 无声那一版的音，不是没有，而是**空的**

`hitosara.mp4` 里**有** `aac` 的音轨。但**内容是纯粹的数字无声**——
实测为 `mean_volume: -91.0 dB` **且** `max_volume: -91.0 dB`（全区间、部分区间都一样）。
**「没有音轨」与「音轨是空的」是两回事。**
所以**在 `+` 的版里，BGM 不是混在下面，BGM 就是这部作品声音的全部。**

⚠️ **不要漫不经心地往无声的文件上「把 BGM 叠上去再调薄」**——
因为要叠上去的对方是空的。**而且，没有检查会为这个出入报警**
（`renders/` 谁都不读）。**所以这张表，是只有人才能读的记录。**

### ⚠️ 包的宣言与文件的声称，互相矛盾

⚠️ **【实测】** 166曲**全部**的 ID3 `comment` 都是 **`made with suno; created=…; id=…`**
——**包宣言「CC0」，但文件自己声称是生成物。**
`soft-gold-sky.mp3` 的声称是
`made with suno; created=2026-03-13T05:06:05Z; id=fd5744ef-b45f-4571-b7d4-ef801b92d95f`。

⚠️ **这是这个基盘的原则本身的实例**——
**「宣言正确，和宣言被照着读，是两回事」。**

**所以:**

- **只在手头看的话，风险很低。**
- ⚠️ **要公开的话，风险是作者的。** 宣言的 CC0，
  **不是分发给他人者能验证的形式**（只要是生成物，权利的链条就闭不上）。
  **要往安全一侧倒，就选宣言者就是作者本人的曲**——例如
  **Incompetech（Kevin MacLeod）的 CC BY 4.0**，是**作者自己宣言的。**
  ⚠️ **CC BY 以署名为条件。所以这张表是必要的。**
