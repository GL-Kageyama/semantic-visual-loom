# 受け火 V2 — §1–20 仕様からの移行記録

**このプロジェクトは、既存の30本の仕様（`video-*/seg-*/wan-full-spec.md`）を
構造化した最初の1本目である。** 仕様そのものは**そのまま残してある**——消していない。

## どの欄が、どこから来たか

**⚠️ この区別が要る。** 機械で写せる欄と、**人が書かなければ存在しない欄**がある。
混ぜると、「検査が通った」が「人が書いた」を意味しなくなる。

| 欄 | 出所 | 機械か人か |
|---|---|---|
| `shot` | ディレクトリ名 | 機械 |
| `spec` | 移行元のファイルパス（`video-NN/seg-MM/wan-full-spec.md`） | 機械 |
| `place` | §4 ENVIRONMENT / Location の `ID` | 機械 |
| `duration` | §1 VIDEO / Basic の `Duration` | 機械 |

| `role` `effect` | **`検証/種別の分類.md` の実測**（§7 Core Event と §9 の器官から人が当てた） | **人** |
| `unit.before` `unit.after` | **`§7 Core Event` から人が要約した** | **人** |
| `mode` | 30本すべて `motion`（実測。§1 に Mode 欄は無い） | 機械 |
| `time` | §2 WORLD の `Time: Time does not flow. There is no morning; only the hour work begins` | 機械 |
| `reference_set` | 台帳から導出（下記） | 機械（台帳から） |

## §1–20 の一対一対応

**20節のどれが、どの欄へ移り、どれが移らないか。** 実測は
`engine/ledger/specmap.py` に**目録として**置いてある——散文で置くと腐るので、
`check.py` が**両方向に閉じているか**を確かめる（L11・L12）。

⚠️ **「移らない」は「失われる」ではない。** 移らない節も**仕様（`spec:` が指す先）には
そのまま在る**。落ちるのは*ショット記録から*であって、*作品から*ではない。

### ⚠️ §18 はモデル固有の投影である——**だから `spec:` はここを指す**

節の名が **`WAN 3.0`** を名乗っている。そして §6 の `REF_FORMAT` が
「**the six §18 slots**」を定義している——**§18 の形は様式カードの持ち物**である。

つまり §18 は**記録ではなく、記録を或るモデル向けに書き出した文**である。
**だから §18 はショット記録の欄にならない。**
そして**だから `spec:` がここを指す**のである——**モデルが変われば §18 だけが差し替わり、
欄（＝台帳が読むもの）はそのまま残る。** これが**モデル非依存**の実装であり、
`WAN 3.0` という節名が、そのことを仕様自身に書かせている。

### ⚠️ 「落ちるのは1本の連続テイク前提の節」は**外れた**

計画はこう予測していた（`実装計画.md` 第3段の1番目、スキーマ/ショット記録.md）:

> 落ちるものは「1本の連続テイク」前提の節のはず。

**測ると外れている。** 実際に落ちるのは **§9・§10・§12・§13・§17・§18** であり、
そのどれも「連続テイクだから」落ちてはいない。**逆に、連続テイクを名指す唯一の節は落ちない**
——§10 Camera Behavior の `One continuous take; no cut until the final.` は
30本のうち2種で、**ほぼ定型でありながら仕様に残る。**

**実際に落としているのは、別の1つの原則である。**

> **台帳がそのショットについて推論するか。**

- **台帳が読むもの** → 欄になる（`time` ← §2、`place` ← §4、`reference_set` ← §6、
  `beats` ← §8、`forbidden_set`・`disclosure_state` ← §16）。
- **台帳が読まないもの** → 仕様に残る（§9–§13・§17・§18）。**§18 がモデルへ渡す材料である。**

これは**開示で決めたのと同じ1つの原則**である——「**状態はショットが持ち、台帳はそれを読む**」。
ここではその裏から見て「**台帳が読むものだけが欄になる**」と言っている。
**予測が外れたのは、理由を「仕様の形」に求めたからである。理由は台帳の側にあった。**

### 対応は検査される（L11・L12）

| 符号 | 何を鳴らすか |
|---|---|
| **L11** | 仕様の節が目録のとおりでない（足された／欠けた／順序が違う）。⚠️ **目録そのものが短くなっても鳴る** |
| **L12** | 欄と節の対応が閉じていない（出所の無い欄／消えた欄を指す宣言／宣言の無い節／**逆向きの漏れ**） |

⚠️ **L12 は両方向を見る。** 節が欄を名指しても、欄が節を名指さなければ、その欄は
**出所を持たない**——誰かが思いつきで足した欄であり、台帳が読むのかどうかも決まっていない。
**片方向だけでは、対応が閉じていることにならない。**

## 台帳からの導出規則

```text
disclosure_state     宣言された変化点のうち、そのショットまでに起きたものを適用する
forbidden_set        まだ起きていない変化点の属性をすべて挙げる
reference_set        OKURIBI.sheet と CROSSING.base は常に。HANA.sheet は 03-3 以降
```

⚠️ **`forbidden_set` は4点でちょうど1つずつ減る。** 変化点と1対1である——

| 変化点 | 落ちる禁止 |
|---|---|
| `ch03-seg03` 少女が現れる | `HANA` |
| `ch04-seg03` 少女が話す | `HANA.speech` |
| `ch06-seg03` 判は送り火の額 | `HANA.mark` |
| `ch08-seg02` 名が明かされる | `HANA.name` |

**だから `forbidden_set` は台帳から完全に導出できる。** そして**だから L9 が鳴る**
——記録は台帳に対して何も新しいことを言っていない。**それは欠陥ではなく、
この2つが同じ一点から出ているという設計の帰結である。**

⚠️ **`attached` を書かなかった理由。** 受け火 V2 には**参照ディレクトリが1つも無い**——
どのショットに何を添付したかの記録が、そもそも存在しない。
**ここで `attached: []` と書いてはいけない。** 空欄は「何も添付しなかった」という
**主張**であり、事実ではない。書かなければ検査器は「記録が無い」と報告する（L6）。
**それは食い違いではない。**

## 開示の独立読み

`disclosure_state` は台帳から写していない。**§16 MUST NOT の生の文面**から読んだ。

```text
「No 花 / no schoolgirl」の節があるか → 無ければ HANA: present、あれば absent
```

**結果は 無 11 本 / 出る 19 本、境界は `03-3` の1箇所だけ。**
`再編成メモ.md` の「花キャラシートは第3章 Clip 3 以降のみ」と一致し、
記録済みの実測（11本すべてが「花を出すな」と書き、03-3 以降の19本は1本も書いていない）を
**独立に再現した。**

**⚠️ 独立に読んだが、一致した。そして一致は独立性の証拠ではない。**

台帳の4変化点は `検証/開示の形.md` が §16 を30本ぶん測って決めたものである。
**同じ原文を、別の道具で読んだにすぎない。** 読む道具が違えば取り逃すものも違う
——[事前検証の実測.md] が記録したとおりである。

**だから `L9` が鳴る。** 記録が持つ遷移は `HANA` の `absent → present` の**1箇所**で、
それは台帳が宣言した位置と完全に一致する。**つまりこの記録は台帳に対して
何も新しいことを言っていない——写したのか、独立に読んだのか、区別がつかない。**

> ⚠️ **訂正。** 一度「§16 を独立に読み直したら L9 が消えた」と記録したが、**あれは誤りである。**
> 実際に止めていたのは別の理由だった——当時 `L9` は、台帳が宣言していて
> **どの記録も書いていない** 3 属性（`HANA.speech` / `HANA.mark` / `HANA.name`）まで
> 比較に入れていた。食い違いに見えたのである。**L6・L7 とまったく同じ罠を、
> 検査器自身が踏んでいた。** 直したら、鳴るのが正しいと分かった。

**他の3つの変化点（`HANA.speech` / `HANA.mark` / `HANA.name`）は、この方法では読めない。**
`HANA.speech` の手がかり（nameplate / subtitle）は30本のうち7本に散在し、
変化点として読めない。`HANA.name` は 08-2 以降も「No name text on screen」が残る——
**名前は口にされるが、画面には出さない**という別の話であり、1つの変化点ではない。

**だから検査器は、この3つを「検査されていない」と報告する。** それが正しい。

### ⚠️ L4 は移植しなかった——**受け火 V2 で 5/5 誤検出**

`D3`（移動の動詞）は**午前二時の57本で 誤検出 0** だった。同じ検査器を
**受け火 V2 の30本に当てると、5件鳴って5件とも誤検出だった。**

| ショット | 語 | 実際の意味 |
|---|---|---|
| ch00-seg01 | `→` | **器官の並び**（手すくう→指頁をめくる→…）。場所ではない |
| ch03-seg03 / ch04-seg03 | `Then` | **時間の接続詞**（Then the 定型句）。移動ではない |
| ch08-seg01 | `moves to` | **「〜しようとする」**（moves to discard her）。場所ではない |
| ch09-seg03 | `walks to` | 頁の外へ歩く。**場所は変わらない** |

> **同じ欠陥が2つの表記で書かれているとき、片方の表記に合わせると、
> もう片方を取り逃す**——これは既に記録のある失敗である。
> **その裏返しが、これである。検出器を片方の作品に合わせて書くと、
> もう片方の作品で誤検出する。**

だから **L4 は L2 と対でしか鳴らさない。** 場所が実際に跨っているときだけ、
移動の語はその裏付けになる。単独なら**註**であって違反ではない。

### ⚠️ `beats[].density` は二値では足りない（実測）

仕様の30本が持つビートは **91個**。数えると——

| 値 | 個数 |
|---|---|
| `held` | **59（65%）** |
| `sparse` | 30（33%） |
| `dense` | 1 |
| `transition` | 1 |

**当初の enum は `sparse \| dense` の二値で、65% が表現を持たなかった。**
二値に収めるには `held` を `dense` に読み替えることになるが、それは**意味を捨てる**——
`held` は「濃い」ではなく**「保たれている」**であり、この作品の地である。
**実測が enum を広げた**（`schemas/shot-record.schema.json`）。

### ⚠️ この作品に `time` は無い

30本すべての `time` は同じ——`境（時刻が流れない）`。
仕様の §2 WORLD が `Time does not flow. There is no morning; only the hour work begins` と書く。

**つまり L3 の欄側の検査は、この作品では空である。**
衣装が「場所×時刻」で決まる作品（午前二時）では意味を持つが、
受け火では衣装は**開示**が決める（制服は 03-3 の少女の出現ととも現れる）。
**同じスキーマが、作品によって別の欄を空にする。**
