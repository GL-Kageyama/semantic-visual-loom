# schemas/ — データ構造の正典

**このリポジトリが持つ構造は、ここが正典である。** `projects/<project>/` の `.yaml` は、この5枚に従う。

## なぜ JSON Schema か

**事前検証が、これを機械で読むからである。** `engine/ledger/` の検査器は「生成を1回も走らせずに設計の破綻を潰す」ために、
ショット記録を読んで判定する。人が読むためだけの形式では、その役に立たない。

日本語の説明は `description` に置く。**構造は英語のキー、説明は日本語**——生成器へ渡る文字列（`Negative`・プロンプト・enum 値）が
英語不変部であるのと同じ理由で、キーは英語のままにする。

## 5枚

| ファイル | 何の構造か | 決定度 |
|---|---|---|
| `bible.schema.json` | **作品台帳**。作品の世界の不変部。プロジェクトに一つ | 低い（不変部と可変部の線引きが未決定） |
| `ledger.schema.json` | **制作台帳**。連続性と開示を**一つのファイルに**持つ。プロジェクトに一つ | 中（開示の形は決着。属性の型が残る） |
| `shot-record.schema.json` | **ショット記録**。1生成に1枚。単体で完結する | 高い（`unit` と `role` が決定済み） |
| `take.schema.json` | **テイク**。標本1つにつき1枚 | 中（検収の層の数に従属） |
| `timeline.schema.json` | **タイムライン**。採用テイクの列 ＋ カット点 ＋ 文字 ＋ 音 | **最も低い**（どれを正とするか未決定） |

## ⚠️ このスキーマが鳴らせないもの

**「一つの変化」の検査は、この層では完結しない。**

`unit` を `{ before, after }` の対にしたのは、「`before` と `after` が同じ」を鳴らすためである。
**だが JSON Schema は2つのプロパティを比較できない**——標準の仕様にその機能が無い。
実際に測った——`{ before: "同じ", after: "同じ" }` を通してしまう。

**逃げ道も測って塞がっている。** `if`/`then` + `const` は**列挙**であって比較ではない
（リテラルを書いた分しか捕まらず、`before`/`after` は自由文なので閉じない）。
`$data` 参照は標準仕様に入らなかった提案であり、参照実装はただのリテラルとして扱う。
（実測は `HISTORY.md`。）

**したがってこの制約は `engine/ledger/` の検査器が負う。**
**「対にした」ことと「対を検査できる」ことは別である。** 対にしただけでは、後者は得られない。

同じ形の穴が他にもある。**JSON Schema が保証するのは「形」であって「意味」ではない。**

| 鳴らしたいこと | 誰が鳴らすか |
|---|---|
| `before` と `after` が同じ | **検査器**（スキーマには書けない） |
| 一環境か（`place` が単数か、`beats` に複数の `place` が現れないか） | **検査器** |
| 一時刻か | **検査器** |
| 種別とモードの食い違いが、判断か事故か | **検査器**（判断なら記録に残す） |
| 参照画像の服装が、そのショットの服装と一致するか | **検査器** |
| `reference_set`（意図）と `attached`（実際）の食い違い | **検査器** |
| 形が正しいか（必須・型・enum・`duration` の書式） | **このスキーマ** |

**どの項目も、生成を1回も走らせずに捕まる。**

## 決定の出所

| 何 | 決定 |
|---|---|
| `unit` = `{ before, after }` | 2026-09-13、著者。自然文では「一変化か」を機械が判定できない |
| `role:` = 必須 | 2026-09-13、著者。空なら、そのショットが何で裁かれるのかが決まっていない |
| `disclosure` = ショットIDをキーにした変化点の列 | `shot:` をキーにする。`at` × `clip:` と Segment ID 列挙は、どちらも「どのショットか」を台帳側の座標で書こうとしているため落ちた |
| `at` = §16 の見出しのレンジ名 | 導出規則は見出しから取る（ショットIDからではない）。87本を測って失敗ゼロ |
| 添付の「実際」をショット記録が持つ | 受け火 V1 は、花が出演しているのに花のシートが無いクリップが2本あり、仕様には添付の宣言が1つも無かった |

## まだ決まっていないこと

**スキーマに `description` として書き込んである。** 主なもの——

- **種別（`role`）の目録。** 12種中5種しか使われていない（実測済み・登録は未決定）
- **運動の層を必須欄にするか。** 「全ショットが持つ」という主張と、空欄を許すかが噛み合っていない
- **`beats` の `density` が二値で足りるか**
- **`disclosure_state` の値の型**
- **`… yet`（前方参照）をどう持つか。** §16 は明かしの**直前**に `no name yet` を立てる。これは状態ではない——これから起きることの予告である
- **添付の保持期間**、**失敗テイクを残すか**
- **編集の出力形式**（OTIO / EDL / FCPXML / 自前レンダ）
