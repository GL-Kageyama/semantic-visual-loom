# 使い方

プロジェクトの記録に対する、事前検証の走らせ方。

**生成はこの基盤の中では走らない**——**著者が手で回し、基盤は記録を読む。**
走るのは、**生成する前に**仕様の段で矛盾を鳴らす検査である（そして生成のあとは、
戻ってきたものの突き合わせ）。それに加えて、**値が既に強制されている行**を刷る道具である。

## 要るもの

`python3` と、**PyYAML と jsonschema**。**インストールの手順は無い。**

```bash
python3 -m pip install --user pyyaml jsonschema
```

⚠️ **Homebrew の Python（PEP 668）では `pip` がそれを拒む**——`--user` と一緒に
`--break-system-packages` を渡す。書き先はユーザーのサイトであり、
**Homebrew のツリーは触らない。**

## コマンド

**コマンドは4つある**——**作品を作るための3つと、リポジトリを保つための1つである。**

```bash
# 検査器——仕様の段で矛盾を鳴らす
python3 engine/ledger/check.py --self-test                 # 検査器が鳴るかどうか
python3 engine/ledger/check.py projects/hitosara           # 1つのプロジェクトの事前検証
python3 engine/ledger/check.py projects/ukebi/ukebi-v2     # 受け火 V2

# 刷る者——仕様のうち、導出できる行。何も書かない
python3 engine/shot/print_spec.py projects/hitosara
python3 engine/shot/print_spec.py projects/hitosara --shot hitosara-ch01-seg04

# カメラの目録——役割や運動に合う技法を引く。何も書かない
python3 engine/shot/camera.py --role 情景 --motion 停止
python3 engine/shot/camera.py --id 007

# 引く道具——光・構図・画風の目録を、それぞれの欄で引く。何も書かない
python3 engine/shot/look.py --light --role 情景
python3 engine/shot/look.py --light --kind 自然 --function 設定
python3 engine/shot/look.py --light --id 055
python3 engine/shot/look.py --composition --role 情景
python3 engine/shot/look.py --composition 三分割
python3 engine/shot/look.py --light ゴールデン --composition 三分割
python3 engine/shot/look.py --style --medium 手描き --star 3
python3 engine/shot/look.py --style 水彩

# リポジトリ自身の文書検査——作品を作るのには使わない
python3 tools/check_i18n.py                                # 文書のミラー
```

**`engine/ledger/check.py`**

| 引数 | |
|---|---|
| （位置引数） | プロジェクトのディレクトリのパス。`--self-test` を付けたとき以外は要る。 |
| `--schemas` | スキーマのディレクトリ。既定は `<リポジトリ>/schemas`。 |
| `--self-test` | プロジェクトを取らない。**全ての例が期待どおりなら `0` で終わる。** |

**`engine/shot/print_spec.py`**

| 引数 | |
|---|---|
| （位置引数） | プロジェクトのディレクトリのパス。 |
| `--shot` | 1本のショットだけを刷る。 |

**`engine/shot/camera.py`**

| 引数 | |
|---|---|
| `--role` | その動きが担える `role`（15の種別の1つ） |
| `--motion` | `MOTION_PATTERNS` の1つ（`停止`・`カメラのみ`…） |
| `--job` | 演出上の仕事（8つのうち1つ。`確立`・`焦点`…） |
| `--position` | `頭`・`中`・`尾`・`つなぎ`・`全編` |
| `--id` / `--name` | 番号か和名で1つ |
| `--medium` | **画風のみ**：媒材の頭の語（`手描き`・`版`・`写真`・`デジタル`・`立体`・`複合`・`任意`）——`--medium 手描き` は `手描き（油）` まで届く |
| `--star` | **画風のみ**：英語での通りやすさ（`3`・`2`・`1`） |
| `--family` | その項目が載っている章 |

**渡した条件はすべて満たすものだけ**が出る。1つ以上は要る。⚠️ **刷るのは目録であって、
決定ではない**——`roles` は担える仕事の集合であり、**どれなのかはショットが決める。**
⚠️ **§18 が運ぶのは `en` の行である**——和名は生成器へ渡らない。

**`engine/shot/look.py`**

| 引数 | |
|---|---|
| `--light` | 光の目録（`references/lighting/`）を読む。**名を添えられる**（`--light ゴールデン`）——その名の一部で絞る |
| `--composition` | 構図の目録（`references/composition/`）を、同じように読む |
| `--style` | 画風の目録（`references/styles/`）を、同じように読む——100の名を、`--medium`・`--star`・`--family` で絞る |
| `--kind` | **軸ごとの語彙**：光なら誰が作るか（`灯`・`自然`・`光学`・`編集`）、構図ならその名が何を指すか（`構図`・`画角`・`配置`） |
| `--role` | その技法が担える `role`（15の種別の1つ） |
| `--function` | 劇的関数（`設定`・`様式美`…） |
| `--job` | 演出上の仕事（8つ）——⚠️ **軸ごとに語彙が違う** |
| `--position` | `頭`・`中`・`尾`・`つなぎ`・`全編` |
| `--id` / `--name` | 番号か和名で1つ |
| `--medium` | **画風のみ**：媒材の頭の語（`手描き`・`版`・`写真`・`デジタル`・`立体`・`複合`・`任意`）——`--medium 手描き` は `手描き（油）` まで届く |
| `--star` | **画風のみ**：英語での通りやすさ（`3`・`2`・`1`） |
| `--family` | その項目が載っている章 |

**渡した条件はすべて満たすものだけ**が出る。1つ以上は要り、**軸だけでは絞り込みにならない**
——道具は100件を全部刷るのではなく、条件を1つ求める。
⚠️ **軸ごとに、受ける絞り込みが違う**——画風に `--role` は無く、光に `--medium` は無い。
**その軸に無い絞り込みは、無視せずに断る**——無視すれば0件が刷られ、0件は
**「その技法が無い」**と読まれる（本当は**「その軸にその欄が無い」**）。⚠️ **§13・§18 が運ぶのは `en` の行
である**——そして `L56` は**先頭の語を活用せずに**それを引く。光の名は名詞だからである。
⚠️ **何にも当たらないことは、目録が空であることではない**——道具はどちらなのかを言う。
⚠️ **`card: —` と刷られた画風は、どのカードも持たない名である**——**その名も使える**：
`en` の行が句であり、一覧が名を知らないカードが何枚あるかは `L59` が報告する。
⚠️ **`en: —` と刷られた構図は `twin` である**——句はカメラの目録に在り、`L54` がそちらで読む。

⚠️ **`check.py` と `print_spec.py` は択一ではない——覆っている範囲が食い違っている。**
**`print_spec.py` が刷る行は、写した瞬間に黙る行である**（だから刷られた各行は、
黙る検査を名乗る）。**つまり `check.py` は、その行を報告できない。** 逆に
**`check.py` が鳴らすものは、`print_spec.py` が導出を断ったものである。**
⚠️ **強制されている行は刷る者に、断られたものは検査器に**——どちらも、相手の範囲を覆わない。

⚠️ **`engine/shot/print_spec.py` は何も書かない**——記録と台帳と作品台帳を読み、
**値が既に強制されている行だけ**を刷る（§1 の作品定数4つ、`Duration`、§19 の `Instance ID`）。
⚠️ **それを貼るのは著者の行為である。** ディスク上の仕様と食い違えば、**両方**を並べて止まる。
導出しないものと、残した穴は [`engine/shot/README.md`](../engine/shot/README-ja.md) に在る。

⚠️ **`skills/` に在るものはコマンドではない**——**Claude Code のセッションへの指示であり**、
**物語を仕様へ変えるのは、この4本である。** 下の **4つの段** を見ること。
⚠️ **すべての Skill が段なのではない**——`direction`（作品の劇作）は**①の中**、
`staging`（カメラを一手に決める）は**②の中**で走り、`review`（評議会）は**④の後に座る**。
**在ることによって段の数は動かない。**
⚠️ **`review` はテイクの `verdict.council` を書き、決して採用しない**——④の後にある
Skill は、⑤ではない。

## 4つの段

**物語が入る。生成器へ渡す文字列が出る。**
⚠️ **4本ともプログラムではない**——セッションへ渡す文書であり、
**このリポジトリに4本のコードは無い。** 走るのは検査器だけである。

| 段 | 渡すもの | 出すもの | 置き場 |
|---|---|---|---|
| **① 分解** | 物語・プロット・草稿 | ショットの列、作品の台帳、開示の変化点 | `bible.yaml`・`ledger.yaml`・`shots/` |
| **② 設計** | ショット1本 | 演出の記録、§1–20 の動画仕様（**§18 の7スロット**）、画像仕様——そして**絵コンテを経由する動画の経路では、`distill-essence-engine` へ渡すボードのプロンプト** | `shots/<id>.yaml`・`specs/video/<id>.md`（**2つの経路を持つ作品は `specs/video/<経路>/<id>.md`**）・`specs/image/<id>.md`・`specs/board/<id>-board.md` |
| **③ 台帳** | ショット1本 | 育てられた台帳と、各ショットの記録に載る導出集合 | `ledger.yaml`・`shots/<id>.yaml` |
| **④ ショット** | 戻ってきたもの | 1枚で立つ記録と、テイク ⚠️ **採用はしない** | `shots/<id>.yaml`・`takes/<id>-<kind>-<n>.yaml` |

**プロンプトが書かれるのは②である。** 7スロットは `Master` / `Visual` / `Motion` /
`Camera` / `Audio` / `Negative` / `Style Motion`——**すべて英語**であり、
**分かれていること自体が要点である**
（[`references/formats/video-spec.md`](../references/formats/video-spec-ja.md) §18）。
⚠️ **別々に渡す。渡るのは §18 だけである**——§19 と §20 は我々自身の記録である。
⚠️ **§17 と §18 の間に立つ `## DIRECTION` は、八つ目のスロットではない。**
`PROMPT_SLOTS` は七つのままである。節は**生成時に `Master Prompt` の先頭へ連結され**、
**スロットにならないままモデルへ届く。** 台帳の `dramaturgy`、ショットの `dramatic`、
§12 EMOTION から英語で書く。**`dramatic` を持たないショットには要らない**——
**`L43` は、節を持つ本数と記録を持つ本数を並べて報告する。**

⚠️ **§18 の見出しはモデルを名乗る。そして動画の経路は3つある。** `L18` はその見出しを
登録簿（`specmap.MODELS`）と突き合わせる——**`WAN 3.0` は `key_image` を取り、
`MINIMAX H3` は取らない。** あちらの添付は**絵コンテの画像**であり、
**その画像を作る紙は `distill-essence-engine` である**（フォーマット `storyboard`、
様式 `luminous-anime`）。ゆえにボードのプロンプトもこの基盤の文書であり、`specs/board/` に住む。
⚠️ **絵コンテは「画像の経路」ではない。** あちらの紙は**文字を描く**——コマ番号・説明文・欄
——そして**画像の経路の床は、画面の文字を禁じる。** ゆえに `key_image` はそれを持てない。
**紙は、撮る前の、動画全体の設計である。** 生成器はそのコマを順に読み、
**各コマをそれ自体で一つのシーンとし、次のコマとは自然なアニメーションで繋ぐ。**
⚠️ **3つ目の経路 `SEEDANCE 2.5` は、既定では何も添えない。** 長い一つのプロンプトを読み、
**そのプロンプトが自前の時計を持てる**（`0-3s:` `3-6s:`）。⚠️ **そして `Negative Prompt` の欄を、
床としては受け取らない**——ベンダーが否定として扱うのは**字幕と音声だけ**であり、
**その欄の残りは散文として読まれる。** **`L30` が鳴るのはこの門である**——経路が
「受け取れないスロット」を宣言し（`specmap.MODEL_UNRECEIVED_SLOTS`）、それを埋めた仕様が報告される。
**それでもこの経路を使う作品は `bible.route_limits_accepted` を書く**——**除外は作品が書く。**
⚠️ **経路は、時間の文法を共有しない。** `MINIMAX H3` に掛かる制約——**渡す文字列と、
紙の文面の両方**——は [`docs/h3-route-ja.md`](h3-route-ja.md) に在り、
`SEEDANCE 2.5` に掛かるものは [`docs/seedance-route-ja.md`](seedance-route-ja.md) に在る。
⚠️ **ボードを検査するものは、まだ無い。** ショットの記録のどの欄もそれを指さないので、
**`check.py` は決して開かない**——**穴であり、穴として報告される**
（[`engine/ledger/README.md`](../engine/ledger/README-ja.md) の `L18` の註を見よ）。
⚠️ **床の節を外せるのは作品であり、作品だけである。** `bible.base_negatives_waived` が
その唯一の席である。⚠️ **2つ目の席がかつて在った**——1つの仕様の §16 にバッククォートの1行を書き、
**そのショットに限り**基盤の節を外す仕組みである。**作った当日に外した**——仕えていた裁定が撤回され、
**それを使う仕様が1本も無くなったからである。** 規則と実測は
[`engine/ledger/README.md`](../engine/ledger/README-ja.md)（`L21`）にある。

⚠️ **呼び出しには名前空間が付く**——`/semantic-visual-loom:breakdown`・`:direction`・`:design`・
`:ledger`・`:shot`・`:staging`・`:review`。

⚠️ **①の入力の形は未定である。** 作品が**プロットで来るのか、脚本で来るのか、小説で来るのか**、
このリポジトリのどこにも書いていない——人かセッションと一緒に読み、**読んだ形を記録すること。**
⚠️ **そしてショットの列にスキーマは無い**——`shot-record` は `duration` を要求し、
**それを決めるのは②である。** だから**①だけでは、検査器が読める記録を出せない。**
⚠️ **②がディスクに乗るまで、検査器は何も読めない。**

⚠️ **⑥構成と⑦検収はその中に無い**——**入力が記録の側に無いからである。**
`clips[]` は定義上、採用テイクの列であり、**`adopted: true` を持つ動画テイクは2本ある**が、
**作品の採用テイクはまだ編集ではない**——どのクリップをどの順で並べたかを記録する場所が無く、
`Project` は `timeline/` を開かない。
⚠️ **動かせない**のであり、⚠️ **空のタイムラインを吐く Skill は、無い Skill より悪い。**
理由は [`projects/hitosara/renders/README.md`](../projects/hitosara/renders/README-ja.md) にある。

## ⚠️ 終了コードを正しく読む

| 終了コード | 意味 |
|---|---|
| **`0`** | **違反**が無い |
| **`1`** | 違反が在った |

⚠️ **`0` は「正しい」ではない。** 報告には**註**——読んだが違反ではないもの——と、
**検査が見なかった範囲**も載る。**報告しない検査は、通った検査と同じに見える。**
数だけを読まず、**註と、検査されていない範囲を読むこと。**

## プロジェクトとは何か

`check.py` は**プロジェクトのディレクトリ**のパスを取り、それを読む。
**何も書かず、`media/` を開かない。**

```
projects/<name>/
├── bible.yaml      # 世界・根本律・視覚言語（要る）
├── ledger.yaml     # 連続性＋開示。ひとつのファイルに持つ（要る）
├── shots/          # 1ショットにつき1枚のショット記録（<id>.yaml）（要る）
├── takes/          # 戻ってきたものの記録
├── specs/          # §1–20 の文書（video/ と image/）、そしてボードのプロンプト（board/）
├── media/          # 生成物の置き場   ⚠️ 基盤はここを開かない
├── renders/        # 編集で出来たもの（作品）
└── timeline/       # 編集
```

⚠️ **そのディレクトリがどこに在るかは、恣意的ではない。そして規則は一方向である**——
**逆は成り立たない。** `projects/ukebi/` がその理由である（**11の生の仕様書の木と、1本の作品**）：

> **すべての作品は、自分のディレクトリに自分の `bible.yaml` と `ledger.yaml` を持つ。
> だが、作品を抱えているディレクトリが、それ自体 作品であるとは限らない。**
> ⚠️ **逆は成り立たない——作品が作品を抱えてはならない。**

⚠️ **`check.py` は再帰しない**——`root/shots/*.yaml` を**平らに**読む。ゆえに
**作品が作品を抱えていると、親を走らせても読まれず、しかも出力はそれを言わない。**
`L29` が、読まれなかった作品を名指しする。

検査が読むのは `bible.yaml` / `ledger.yaml` / `shots/` / `takes/`、そして
**ショット記録が指している仕様の文書**（`spec:` と `key_image:`）である。
⚠️ **`specs/board/` はその中に無い**——**ボードを指す欄が無い**ので、
絵コンテのプロンプトは**どの層の外にも在る。** **それは免除ではなく、穴である。**

⚠️ **`bible.yaml` / `ledger.yaml` / `shots/` が無いことは、黙って空にされず、報告される。**
そして**1本読めなくても、検査は最後まで走る**——止まると、
**壊れた1本が他のすべての報告を隠す。**

⚠️ **`media/` と `takes/` は別である。** 置き場と記録——**置いたことは、記録したことではない。**
だから `media/` に在るのにテイクが無い、という状態がありうる。
**検査は `media/` を開かないので、記録と実物の食い違いは鳴らない**——それは穴であり、穴として報告される。
**`takes/` が空なら「テイクの記録が1本も無い」と言う。0件は合格ではない。**

⚠️ **`projects/` には2種類が同居している**——**生の仕様書**と、**構造化した記録**
（`bible.yaml` / `ledger.yaml` / `shots/`）。

⚠️ **`projects/ukebi` と `projects/gozen-niji` は、生の仕様書であってプロジェクトではない。**
`bible.yaml` / `ledger.yaml` / `shots/` を持たないので、検査を走らせると
**「読めていない」**が並び、`L0` が**「ショットが1本も無い。検査は何も見ていない。」**と鳴る。
**これは誤りではなく、正しい振る舞いである。**

⚠️ **生の仕様書の側には、生成物を置いていない**——**記録と仕様だけである。**
**古い生成物は、作品のクォリティの統一度を下げる。**

⚠️ **ただし `reference/` の参照資産は残してある**（**9種**。各セグに複製されている）。
**それは生成物ではなく入力である**——そして**「どのセグに、何を添付したか」の唯一の記録である**
（`wan-full-spec.md` は参照を `REF_STYLE` / `REF_SOURCE` としか書かない）。
⚠️ **消せば、添付の記録ごと消える。** この数の裏取りは `HISTORY.md` にある。

⚠️ **`renders/` は編集で出来たもの（作品）の置き場であり、`media/` は標本の置き場である。**
**標本と作品は場所で分ける**——名前では分けられない。
⚠️ **`timeline/` の空は、それすら報告されない**——まだ誰も開かないからである。
**報告しない検査は、通った検査と同じに見える。**

## 層

検査は**59の層、`L0`–`L59`** と、スキーマの形の検証から成る。
⚠️ **`L35` は予約であって、書かれていない**——ゆえに**番号が1つ飛ぶ。** `L0`–`L59` は60の番号で、
**59の層である。** ⚠️ **`L34` と `L36` は曲を読む**——時間の主を曲と名指していない作品は、
**「何も見なかった」と言われる**——**黙ってはいない。**
⚠️ **`L37` はショットの内側を読む**——ビートが `duration` を敷き詰めているか——そして
**曲の有無にかかわらず、すべての作品を読む。** ⚠️ **`L38` は動画仕様の読み口を読む**——
演出要約がそれを開いているか——そして**動画仕様を1本も持たない作品は、
「何も確かめなかった」と言われる**——**「綺麗である」ではなく。**
⚠️ **`L39` は、1つのショットが2つの経路に置かれているとき、その対を読む**——経路の名の
ディレクトリに並ぶ仕様である——そして**片方しか持たない作品は、「対を1つも読んでいない」と言われる。**
⚠️ **`L40`–`L47` は劇作を読む**——そして**それぞれは版ではなく、記録によって点く**：
`L40`/`L43`/`L47` はショットの `dramatic` で、`L44` は `beats[].intensity` で、
`L41` は `acts`/`sequences` で、`L42`/`L45` は §6 `REF_FORMAT` が名指す文法で、
`L46` は `grammar:` で開く `aim` で点く。⚠️ **`L48`–`L50` は、シーケンスを自分のショットと照合する**——
`withheld`・`cuts`・`tempo` であり、**どれも宣言しないシーケンスは「何も拘束していない」と言われる。**
⚠️ **`L51` はショットの `population` を §18 と照合する**——数は `Master Prompt` の名指しと
`Negative Prompt` の写しになり、両方向を読む——そして**数を宣言しないショットは、
「何も読んでいない」と言われる。** ⚠️ **`L52` はショットの `body_parts` を読む**——枠が身体のどこを写し、それが何本入るかを、
部位ごとの同じ2句と、そして `population` と照合する：**人数は身体を数え、
この欄を要求した失敗は肢で起きた。**
⚠️ **`L53` はカメラの目録の形を読む**——`motion_pattern`・`role`・関数・文法カードが
すべて語彙に引けるか——そして**`L54` は §18 の `Camera Prompt` を、目録の `en` の句へ当てる。**
⚠️ **`L54` が鳴るのは1つだけである**：ショットが「カメラは全編動かない」と言い切りながら、
`travels` が真の技法を名乗ったとき。**目録の句を1つも使っていない作品は、
「どれにも当たらなかった」と言われる**——**その註が、使われている度合いの実測である**——
欠陥ではない。
⚠️ **`L55` は光の目録の形を読む**——`kind`・`role`・関数・文法カードがすべて語彙に引けるか——
そして**`L56` は §13 `LIGHTING` を、その目録の `en` の句へ当てる。**
⚠️ **`L56` に違反は無い**：§13 を持つ動画仕様が何本か、どの光を名指したか、
何も名指さないのが何本か、**そして §13 が名指した光を §18 の `Visual Prompt` が運んでいない
ショットがどれか**を報告する——これも註である：目録の `en` は普通の名詞でもあり
（`Dawn`・`Direct sun`）、散文は技法を名乗らずにその語を使う。
⚠️ **先頭の語を活用しない**——光の名は名詞であり、
`Bloom` が `the source blooms` に当たってはならない。
⚠️ **`L57` は構図の目録の形を読む**——`family`・`kind`・`role`・関数・文法カードがすべて語彙に
引けるか——**そして、1つの技法を2つの目録が持つことから来る2つの門を閉じる**：
`twin` を持つ項目は `en` を持たず（逆も）、行き先はカメラの目録に実在し、
**構図の句がカメラの目録にも載っていれば、誰も宣言していない第二の住まいである。**
29件が `twin` である——**その重なりは出典の事実であり、欠陥ではない。**
⚠️ **`L58` は §18 の `Camera Prompt` を、その `en` の句へ当てる**——`L54` と同じスロットを、
別の問いで——**そして鳴るのは1つだけである**：`079` 一つだけの構図・`080` 群衆の構図
（名が枠の人数を決めてしまう2件）を名乗ったショットの記録の `population` が、名と食い違うとき。
⚠️ **`population` を書いていない記録は註である**——`L51` が同じ空白を註にしたのと同じである。
**構図に当たった `Camera Prompt` が何本かが、使われている度合いの実測である。**
⚠️ **`L59` は画風の目録の形を読む**——`family`・`star`・`medium` の頭が語彙に引け、
同じ項目が `card` と `near_card` を両方持たないこと——**そしてそれ以外は何も閉じない**——
**加えて被覆を報告する**：届く棚に様式カードが何枚あり、一覧が何枚の名を知り、
**どれが名乗られていないか。** ⚠️ **開けないカードは違反ではなく註である**——
カードはこのリポジトリの外に在る。⚠️ **この軸の層は `L59` だけで、作品を1本も読まない**——
`L20`・`L31`・`L32` が**すでに作品の側から様式を読んでいる**からである——
**1枚のカードの4人目の読み手は、片方を直して、もう片方を腐らせる。**
**どれも書いていない作品は、それらに落ちていない**——
註が、見たショットの数を言う。各層が何を読み、何を読まないかは
[`docs/dramaturgy-ja.md`](dramaturgy-ja.md) と [`docs/cards-ja.md`](cards-ja.md)、
そして [`engine/ledger/README-ja.md`](../engine/ledger/README-ja.md) の層の目録に在る。
**ひとつの判定ではない**——層はそれぞれ独立に鳴り、**見た数とともに**報告される。

⚠️ **何も見なかった層は註として報告され、何も見なかった層は、通った層とまったく同じに見える。**
たとえば `key_image` についての層は、テイクが `key_image` を持たないプロジェクトでは鳴れない——
**比べる相手が無いからである。** **0 は、その層が同意した証拠ではない。**

**層は [`engine/ledger/README.md`](../engine/ledger/README-ja.md) に書いてある**——
各層が何を読み、何に鳴り、**何を見ないか。**

## 文書の検査

```bash
python3 tools/check_i18n.py --self-test   # 各規則の、鳴る例と鳴らない例
python3 tools/check_i18n.py               # 実物
```

⚠️ **見たファイル数と、不変とみなしたブロックを報告する**——
それが無ければ、**何も見なかった検査が、通った検査と同じに見える。**
⚠️ **散文が正しく訳されているかは見ない**——意味が食い違っていても、
**行と見出しが合っていれば通る。**

⚠️ **この検査が見る方式**：正典は**接尾辞を持たず**、ミラーは**同じディレクトリ**に
**接尾辞方式**で並ぶ（`README.md` / `README-ja.md` / `README-zh.md`）。
**`-en` のミラーは作らない**——正典が英語だからである。
⚠️ **サブフォルダ方式（`ja/` `zh/`）は使わない**——**正典とミラーの深さが変わらない**ようにするためである。
⚠️ **開発の作業言語は日本語のままである**（コミットメッセージ・`HISTORY.md`・会話）が、
**文書の正典は英語である。** この2つは別である——**仕事をする言語**と、**文書が権威を持つ言語**である。
**26文書 × 3言語が揃っており**（`tools/check_i18n.py` が正典として報告する本数である）、
規則は [`CLAUDE.md`](../CLAUDE-ja.md) にある。
